ways to use wingthing

Wingthing provides three pieces you can compose. A roost coordinates access, a wing supplies a machine, and an egg wraps one durable agent session. The patterns change who drives the egg and where it runs.

open the patterns skill

roost

Login, identity, policy, and routing for people and agent clients that share infrastructure.

wing

A machine that runs eggs. It can connect to a hosted roost or live inside a self-hosted one.

egg

An owner-scoped agent or terminal with a PTY, sandbox policy, and durable lifecycle.

01
humanlocal

use it as a local sandbox

Start Claude, Codex, or another agent inside an egg on the current machine. The egg applies the project sandbox policy and keeps running across terminal disconnects.

you → wt egg → sandboxed agent

agentlocal

give your AI sandboxed sub-agents

Connect a main Codex or Claude session to Wingthing's typed interface. It can launch owner-scoped eggs, select a model, wait for completion, and read semantic results.

your AI → local MCP → owned egg → result

03
humanremote

reach your machine from the web

Run a wing on a workstation and connect it outbound to the hosted roost. Open and resume its eggs from a browser without an inbound port.

browser → hosted roost → your wing → egg

04
teamshared host

share a roost over the web

Several people log into one roost and run agents on its hardware. Each egg has an owner. A ticket workspace can be shared separately when the work calls for it.

team browsers → shared roost → owner-scoped eggs

agentshared host

let your AI use a shared roost

Codex or Claude authenticates with the person's Wingthing login and orchestrates that person's eggs on shared hardware. The provider login stays in the owner's agent home.
