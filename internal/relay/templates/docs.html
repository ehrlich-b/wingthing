documentation

Wingthing is a typed agent manager for durable agent runs and terminals across local and remote wings, with human takeover when useful.

quickstart

give Codex or Claude access to local agents

$ curl -fsSL https://wingthing.ai/install.sh | sh

# Codex
$ codex mcp add wingthing -- wt mcp stdio --client codex

# Claude Code
$ claude mcp add --scope user wingthing -- wt mcp stdio --client claude

Restart the client, then ask it to call wingthing_capabilities. It can start persistent terminals or headless runs, wait for results, steer work, and stop it.

run your own private browser portal

$ wt roost start --https # portal + gateway + local wing
$ open https://localhost:8443

This self-hosted path needs no Wingthing account. WT creates a localhost-only certificate on demand, installs only its public CA for your current user, and keeps its private keys on this machine.

give an agent access to all your remote wings

On every execution machine, install and authenticate the provider CLIs that may run there, then log in and start its wing:

$ wt login
$ wt start

On the parent-agent machine, log in to the same account and register the direct connector. If that machine is also an execution wing, it is already logged in:

$ wt login
$ codex mcp add wingthing -- wt mcp connect --client codex
# or: claude mcp add --scope user wingthing -- wt mcp connect --client claude

The agent calls wing_list, then passes an explicit wing_id to every operation. The hosted service supplies the access-filtered directory and WebRTC signaling; MCP payloads travel directly between the connector and selected wing. The first release expects the peers to share a LAN or tailnet unless you configure STUN or TURN under ice_servers in ~/.wingthing/wing.yaml; the several-computer pattern includes the exact YAML shape.

use the durable terminal yourself

$ wt terminal --name work
$ wt attach work

optional hosted portal

$ wt login
$ wt start
$ open https://app.wingthing.ai

Free accounts see wing readiness and direct-agent setup in the portal. Accounts with hosted relay access can also start and resume browser terminals. The public direct-free service does not let an account grant itself relay access; Pro and team relay entitlements are provisioned separately.

Your machine is a wing, the runtime that owns the processes and workspaces. An LLM manages it through MCP; a person can use the same runtime through the CLI or browser. The hosted service coordinates direct connections by default. Pro includes its encrypted browser-terminal and control relay; the native connector never silently changes from direct transport to relay transport.

overview

wingthing runs Claude Code, Codex, Ollama, and other AI agents behind one local control plane. The interface can be a CLI, browser, or MCP client. Execution stays on the wing where the selected workspace and hardware live.

termwhat it is
portalThe inventory and controls presented to a person or LLM. The browser and MCP are portal adapters, though they do not yet expose every object with full parity.
wingOne machine running Wingthing. It owns its process, terminal, task, workspace, and agent-home state.
sessionA persistent interactive PTY for an agent, shell, or command.
runA supervised headless agent task with semantic status, events, output, and errors.
eggThe process, PTY, sandbox policy, and local control socket behind a session.
roostThe self-hosted bundle started by wt roost start: a portal and gateway with an embedded wing. Other wings can register with its gateway.

wingthing.ai is the hosted identity, directory, and connection-coordination service. Think of it as a tailnet control plane for wings: it introduces authenticated peers, while the free native-MCP data path is direct. The optional hosted relay carries encrypted browser-terminal and control payloads for Pro users. It is not a roost under the stricter self-hosted-bundle definition above.

agent control

The MCP server lets a parent LLM discover and operate Wingthing without scraping terminal output. Use wt mcp stdio for the same host and wt mcp connect for an explicitly selected remote wing. Use agent_run for semantic task state. Use agent_start when a person should be able to attach to the persistent terminal.

placementcurrent contract
execution wingLocal stdio executes on its host. Direct remote calls require the selected wing_id. A roost HTTP MCP endpoint controls that roost's built-in wing; Wingthing never silently substitutes a different target.
workspacePass an existing cwd on the execution wing. Wingthing does not create, clone, upload, or synchronize the repository or its untracked files.
displayagent_run has semantic status and a final result but no live browser view. agent_start creates a PTY a person can attach to through the CLI, SSH, or an entitled/self-hosted browser.
credentialsThe provider CLI uses the execution owner's agent home on that wing. Shared hosts keep those homes separate. Provider tokens and SSH keys do not belong in prompts or MCP arguments.
durable memoryTasks, results, messages, and threads stay in that wing's ~/.wingthing/wt.db; terminal state stays under ~/.wingthing/eggs, optional prompt memory under ~/.wingthing/memory, and provider history in the provider home. WINGTHING_DIR changes the Wingthing state root. None of this is replicated between wings automatically.

A terminal survives client detachment. A run's record and result persist, but an active headless run still depends on its supervising Wingthing process. Keep the returned run or session ID together with its owning wing for every later operation.

$ codex mcp add wingthing -- wt mcp stdio --client codex
$ claude mcp add --scope user wingthing -- wt mcp stdio --client claude

The main operations are capability discovery, sandbox explanation, terminal lifecycle, agent run lifecycle, bounded loops and dependency graphs, and owner-scoped messages. Every model-reachable operation should have a principal, grant, bound, and audit record.

Remote MCP has no mutable current wing: every wing-owned call requires wing_id, and results include the owning wing. The HTTP MCP endpoint remains available for self-hosted compatibility. Independent roost federation and native passkey ceremony for locked wings are still follow-up work.

installation

The Wingthing runtime and SQLite storage ship in one binary for macOS and Linux, x64 and arm64. Install the agent CLIs you intend to run separately. Trusted localhost HTTPS on Linux also needs certutil from libnss3-tools or nss-tools.

$ curl -fsSL https://wingthing.ai/install.sh | sh

Installs to ~/.local/bin/wt. Set WT_INSTALL_DIR to change the location. The installer verifies the release checksum and confirms that the binary implements the command surface documented by this site before atomically replacing an existing installation.

Or grab the binary from GitHub releases.

To update:

$ wt update

wing setup

Three commands to go from install to remote access:

$ wt login # authenticate with the hosted portal
$ wt start # start the wing daemon
$ open https://app.wingthing.ai # wing readiness and direct setup

wt start runs the wing as a background daemon. Hosted accounts with relay access also get browser terminal controls; direct-only free accounts get the native connector instructions instead. Use wt wing start --foreground for debugging.

Other wing commands:

$ wt wing status # check daemon status + active sessions
$ wt stop # stop the wing daemon

wing configuration

Wing settings live in ~/.wingthing/wing.yaml. You can edit the file directly or use the CLI:

$ wt wing config # view current config
$ wt wing config set org=myteam # set a value
$ wt wing config set audit=true # enable session audit recording
$ wt wing config set hosted_relay=deny # require direct payload transport

The daemon picks up changes via SIGHUP. See the reload column for what requires a restart.

Direct MCP policy is enforced by the wing after the coordinator-authenticated identity arrives. Grant and bound fields are not accepted from tool arguments. Malformed policy or unknown grant names fail closed instead of starting with unrestricted direct access.

Hosted-relay denial is enforced before forwarding by a current gateway and again by the wing. The effective value appears in authorized capability metadata; audit records contain no command, path, terminal, or tunnel payload.

Downgrade boundary: a wing binary from before hosted_relay existed ignores this field and resumes the historical relay behavior. If deny is a security requirement, stop or isolate the wing before installing an older binary.

access control

By default, anyone with your account credentials can start sessions on your wing. Locking it adds a second factor using passkeys - the same WebAuthn standard behind "Sign in with Face ID" and "Sign in with Windows Hello."

A passkey is a cryptographic credential stored in your password manager (1Password, LastPass, iCloud Keychain, Bitwarden) or your OS (Touch ID, Windows Hello, Android biometrics). Most people already have one and don't know it.

When your wing is locked, browsers must prove they hold a passkey whose public key is pinned in the wing's local allowlist before the wing will start, control, or spectate a session. The wing generates one-time challenges, fully validates the WebAuthn context and signature, and binds the resulting token to the browser encryption key and gateway user.

lock your wing

$ wt wing lock

Once locked, the browser shows an "authenticate with passkey" button when you open a session. Click it, verify with your fingerprint or password manager, and the session starts. The wing issues a client-bound token that's valid for the rest of the boot; set auth_ttl to require periodic re-authentication.

manage the allowlist

When locked, only passkeys on the allowlist can access the wing:

$ wt wing allow # list allowed users
$ wt wing allow --email user@co.com # allow a specific user
$ wt wing allow --all # allow all org members
$ wt wing revoke user@co.com # remove from allowlist
$ wt wing revoke --all # clear the allowlist

unlock

$ wt wing unlock

Removes the passkey requirement. Sessions start without a second factor.

The allowlist lives in wing.yaml on your machine. The gateway stores your passkey's public key and credential ID so it can hand them to your wing during wt wing allow. The security model assumes the gateway is not compromised at the time you add a key. After that, verification happens entirely on the wing.

organizations

Orgs let a team share wings. Create one from the web UI (account page), then invite members by email. Members see all wings in the org.

To attach a wing to an org:

$ wt wing config set org=myteam

Or pass it at start time:

$ wt start --org myteam

Org wings show up for all org members in the web UI. Combine with wt wing lock to require passkey auth - org membership gets you visibility, but the wing owner controls who can actually start sessions.

shared wings

Multiple users can share a single wing. Each user gets an isolated home directory, and you can restrict which folders each person sees.

adding users

Set up OAuth on your roost (GitHub or Google), list the permitted account emails in WT_ROOST_ALLOWED_EMAILS, and let those users log in through the browser. Each enrolled user gets their own home directory at ~/.wingthing/user-homes/<hash>/ with shell configs and agent binaries symlinked from the host. The owner gets a per-user home too - there's no bypass for local users.

OAuth proves identity; it does not decide who belongs on a private roost. If the enrollment list is empty, any account accepted by the configured OAuth provider may enroll. Set the list on every internet-reachable private roost unless the provider or ingress already restricts membership.

restricting paths

By default, all users see all configured paths. Add members to restrict access per folder:

# wing.yaml
paths:
  - ~/docs                                    # everyone
  - path: ~/repos/api
    members: [alice@co.com, bob@co.com]     # only alice and bob
  - path: ~/repos/infra
    members:
      - carol@co.com                        # only carol

Owners and admins always see everything regardless of member lists.

admin role

Add emails to the admins list in wing.yaml. Admins see all sessions and all paths - same visibility as the wing owner.

# wing.yaml
admins:
  - admin@co.com
  - ops@co.com

agent settings

Override agent config for all users on a wing with agent_settings in egg.yaml:

# egg.yaml
agent_settings:
  claude: /opt/wingthing/claude-settings.json

Host settings take precedence over user preferences. For Claude, apiKeyHelper in the settings file keeps ANTHROPIC_API_KEY out of the agent's environment.

preview panel

An agent can open a panel next to the terminal by writing $WT_PREVIEW_DIR/$WT_PREVIEW_FILE. The file is consumed - it disappears once the panel picks it up, which is how the agent knows the preview is live. Write it again to update the panel, or write an empty file to close it.

The first line selects the mode:

first linepanel shows
url:<url>the reviewed address with load, copy, and open controls; no request happens until you choose load or open
file:<name>the rest of the file, with a download button
anything elsethe whole file rendered as markdown

Show a deployed app:

echo "url:https://example.com/apps/$WT_USER/tracker/" > "$WT_PREVIEW_DIR/$WT_PREVIEW_FILE"

Show a file the user can download. The name after file: sets both the download filename and its content type - report.csv downloads as CSV, main.go as Go source:

{
  echo "file:report.csv"
  cat report.csv
} > "$WT_PREVIEW_DIR/$WT_PREVIEW_FILE"

Files ending in .md render as markdown; everything else is shown as plain source. Content is text - the panel renders it in a network-inert sandboxed iframe with no scripts, active links, image requests, or raw HTML. Binary files aren't supported; serve those over a URL instead.

A URL comes from the agent, so Wingthing shows it without fetching it. Review the address before choosing load preview or open. Once chosen, the request comes from your browser and is outside the egg's network allowlist; the embedded page receives an opaque sandbox origin and no referrer.

Markdown with no file: header still works and downloads as preview.md:

cat > "$WT_PREVIEW_DIR/$WT_PREVIEW_FILE" << 'EOF'
# Backup Status

| Partner | Last Backup | Status |
|---------|-------------|--------|
| Acme | 2h ago | OK |
EOF

idle timeouts

Kill sessions that go quiet. Set idle_timeout in wing.yaml:

# wing.yaml
idle_timeout: 4h

A session is idle when there's no output from the agent and no input from the user. Agent thinking generates PTY output, so active sessions won't be killed. Default is disabled - sessions run until stopped manually.

egg configuration

Without an egg.yaml, the sandbox applies opinionated defaults: CWD is writable, home is read-only, sensitive directories (~/.ssh, ~/.gnupg, ~/.aws, etc.) are denied, and only essential env vars pass through. ~/.ssh/known_hosts is preserved read-only so SSH can verify host keys without prompting (add deny:~/.ssh/known_hosts to disable this). Network is blocked except for exactly what your agent needs - each agent has a profile declaring its API domains, env vars, and config directories. Claude gets api.anthropic.com, Ollama gets localhost, etc. You don't configure any of this.

A local CONNECT proxy enforces domain-level filtering - agents can only reach their declared APIs, not the entire internet. On macOS, Seatbelt permits only the proxy endpoint. On Linux, every sandbox keeps a route-less network namespace and an inherited-FD relay exposes only the proxy and explicitly declared host-loopback ports. Removing HTTPS_PROXY does not create a route.

Drop an egg.yaml in your project to customize. Configs are additive - you only declare what you're changing from the defaults.

Place egg.yaml in your project directory for per-project config, or in ~/.wingthing/egg.yaml for global defaults. Project configs are discovered automatically. Use the sandbox builder on the homepage to generate configs visually, or install the Claude Code skill for an interactive security interview that generates hardened configs.

Example egg.yaml:

fs:
  - "ro:~/.ssh"         # override the default deny for ~/.ssh
network:
  - "github.com"       # add a domain on top of agent defaults
env:
  - SSH_AUTH_SOCK       # pass SSH agent socket
dangerously_skip_permissions: true

The sandbox auto-injects mounts for the agent binary's install root and config directory, so you don't need to know where Claude or Codex is installed. Use base: none for a blank slate if you want full control.

self-hosting

Run your own roost: a browser portal, gateway, and embedded wing in one process. The runtime is one binary plus SQLite and needs no hosted Wingthing service. Local HTTPS trust on Linux additionally uses certutil from libnss3-tools or nss-tools.

quick start

$ wt roost start --https

Open https://localhost:8443. On first use, WT creates a localhost-only CA and server certificate under ~/.wingthing/local-tls. Both private keys stay mode 0600 on this machine. WT installs only the public CA certificate in the current user's trust store. The browser uses HTTPS on port 8443; the embedded wing uses a separate loopback-only HTTP endpoint on port 8080.

Use wt local-cert status to inspect it and wt local-cert remove to remove the public CA from this user's trust store. Omit --https to keep HTTP. Single-user/no-login mode still binds the implicit listener to 127.0.0.1:8080, refuses explicit non-loopback listeners, and rejects non-loopback Host headers plus cross-origin browser mutations and WebSockets. Authenticated shared deployments keep their configured listener and externally provisioned HTTPS.

multi-user

Same command, add OAuth env vars and an exact email enrollment list. Now those people can log in.

$ WT_BASE_URL=https://roost.example.com GITHUB_CLIENT_ID=xxx GITHUB_CLIENT_SECRET=yyy WT_ROOST_ALLOWED_EMAILS=alice@example.com,bob@example.com wt roost start --addr :8080

Or use Google OAuth with GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET. The allowlist uses exact, case-insensitive email matches and applies to browser sessions, device tokens, wing inventory, and MCP authorization. Connect additional wings from other machines with wt login --roost https://my-roost.example.com and wt start --roost https://my-roost.example.com. Or set roost_url in ~/.wingthing/config.yaml to avoid passing the flag every time.

Public/shared and organization roosts keep their existing externally provisioned HTTPS. Do not add the local --https flag to an OAuth roost; terminate its public TLS at Caddy, nginx, your VPN proxy, Fly, or another ingress.

running separately

If you need the gateway and wing on different machines, terminate valid HTTPS at the gateway ingress, configure OAuth and the same exact enrollment list, and run them as separate processes:

$ WT_BASE_URL=https://roost.example.com GITHUB_CLIENT_ID=xxx GITHUB_CLIENT_SECRET=yyy WT_ROOST_ALLOWED_EMAILS=alice@example.com wt serve --addr :8080 # gateway only
# on another machine:
$ wt login --roost https://roost.example.com
$ wt start --roost https://roost.example.com # wing only

[Service]

architecture

The intended architecture is one wing-owned control contract with CLI, browser, stdio MCP, and HTTP MCP adapters. Today the browser and MCP share the underlying session state when they address the same wing, but the adapter paths are not fully converged.

For an account or self-hosted policy with browser-relay access, the shipped gateway forwards application ciphertext between browsers and wings during normal operation. Free native-MCP clients instead send their operation payloads directly to a wing. The gateway owns accounts and routing, sees wing/session identifiers, selected agent and working-directory metadata, timing and sizes, and serves the browser code.

how the pieces connect

Your wing opens an outbound WebSocket to the gateway and holds it open. When an entitled or self-hosted browser opens a terminal, the browser connects to the gateway over a second WebSocket. The gateway matches them by wing ID and forwards messages both ways. Content payloads use Wingthing's application encryption; routing envelopes and metadata remain visible. A free native-MCP client uses the gateway only to discover and establish its direct connection.

encryption

The browser keeps an X25519 identity key for the tab and the wing has a persistent X25519 identity key. They derive separate AES-GCM keys via HKDF for PTY and tunnel payloads. Terminal I/O, encrypted controls, file listings, session history, and audit data are ciphertext as far as the as-built gateway is concerned. The browser pins the first wing key it sees and rejects later changes. Because the wing key is persistent, Wingthing does not currently claim forward secrecy against later theft of that key.

passkey auth

Encryption keeps the gateway from reading your data. Passkeys control who can start sessions in the first place. When your wing is locked, the browser sends a WebAuthn assertion directly to the wing inside the encrypted channel. The gateway forwards the blob but can't read or forge it. The wing verifies the signature against its local allowlist and issues a boot-scoped nonce for subsequent requests.

what the gateway stores

The gateway database contains account and organization records, login and device credentials, passkey public data, entitlement and usage records, content-free audit metadata, OAuth client registrations, and operational configuration. It does not store terminal bytes, file contents, or session recordings. In an all-in-one roost, the embedded wing separately keeps its local session and task state on the same operator-controlled host.

security

Three security domains, each solving a different problem.

the egg: protecting you from the agent

Agents run inside a platform-native sandbox - Seatbelt on macOS, user namespaces + seccomp on Linux. The sandbox controls filesystem access, network reach, and system calls. Configure it with egg.yaml; see egg configuration.

the wing: protecting you from the gateway

Terminal and tunnel payloads between the shipped browser and wing are application-encrypted (X25519 + AES-GCM). Wings connect outbound only - no inbound ports or static IP. Locking adds a locally verified passkey. The hosted browser still trusts JavaScript delivered by the service, so this is not a malicious-service-resistant guarantee; see the security model for the exact boundary.

the gateway: controlling access

The gateway handles login (OAuth, device auth) and routes connections to the right wing. When a wing is locked, the gateway stores passkey credential IDs so it can hand them to the wing during wt wing allow, but the WebAuthn verification happens on the wing. See access control.

browser-local data and previews

For fast restore and session cards, the browser stores up to 200,000 serialized terminal characters plus a WebP thumbnail per session as plaintext in this site's local storage. Other cached inventory and layout data also lives there. Browser profiles, extensions, and scripts with access to this origin can read it; clear the site's browser data to remove it.

Agent-authored Markdown previews are network-inert. Agent-authored URLs are displayed but not fetched until you choose load preview or open. After that choice, the request comes from your browser and is outside the egg's network allowlist. The iframe uses an opaque sandbox origin and no-referrer policy, but the destination still receives the request and its network-level metadata.

sandbox limits

The sandbox is not a container runtime. Known gaps:

  • Linux protocol coverage is intentionally narrow. The agent has no default route. HTTPS reaches a domain-filtering CONNECT proxy through the one inherited relay, and declared network.local_ports reach only those host-loopback TCP ports. Arbitrary UDP, ICMP, and non-proxied TCP are unavailable; a client that ignores HTTPS_PROXY fails closed.
  • Agent credentials are readable. API keys and config files needed by the selected agent are mounted into the sandbox. The restrictive default network profile limits egress to that agent's declared service domains, but every endpoint in the effective allowlist is a possible exfiltration destination. Adding a domain or using network: "*" deliberately broadens that boundary.
  • HOME is readable. The agent reads your codebase. Add "deny:~/.secrets" to the fs list to hide sensitive directories.
  • Agent config is writable. ~/.claude/ and similar directories must be writable for the agent to function.
  • Resource limits are Linux-only. macOS agents can consume unbounded CPU and memory. On Linux, cgroups v2 limits real memory (RSS) and process count; rlimit covers CPU time, virtual address space, and file descriptors. Cgroups require v2 with delegation. Falls back to rlimit-only when unavailable.

These are on the roadmap. If any of these are blocking you, file an issue - it helps us prioritize. If you need hard isolation today, run wingthing inside a VM or container.
